一、仓库现状概览

基于对 README.md、AGENTS.md、根目录 SKILL.md、4 个 workflows、9 份 references 契约与 6 个脚本的通读。

agent-group-orchestrator 是一个可复制安装的项目级多智能体编排技能包。根目录 SKILL.md 按意图路由到 init、orchestrate、memory-sync、review 四个工作流。 核心思想：主 agent 只充当 main-orchestrator 监督者（目标澄清、任务拆解、worker 选择、风险门禁、记忆同步）， 所有实际工作（开发、测试、调研、评审）必须经 sub-agent 后端派发给注册的 worker 执行； 全部编排状态落在目标仓库的 .agent_group/、.claude/agent_group/ 或 .codex/agent_group/，以纯文本文件为唯一事实源。

组成内容
SKILL.md 与 workflows/一个技能入口，路由到 init（初始化实例）、orchestrate（自动编排）、memory-sync（记忆同步）、review（评审）
references/（9 份契约）路由策略（4 类常用 DAG）、R0–R4 风险门禁、worker registry、sub-agent 执行契约、输出契约、目录契约、记忆 schema / 生命周期 / 同步 SOP
scripts/（6 个，纯标准库）init、validate（--strict）、路径解析、tasks.csv → Mermaid DAG 渲染、compact_memory 归档、check_public_safety 泄密扫描

任务模型tasks.csv + depends_on 列表达任务 DAG，状态枚举 todo/in_progress/blocked/review/done/dropped

二、本仓库差距分析

由独立差距分析代理通读全仓库产出：6 项优势、12 项差距、6 项风险。

✅ 现有优势

契约文档体系完整且相互引用一致：references/ 下 9 份文档（routing-policy、sub-agent-execution、risk-policy、memory-lifecycle、memory-schema、output-contract、worker-registry、directory-contract、memory-sync-sop）明确定义了监督者/执行者边界、R0-R4 风险门禁、worker 输出契约和记忆三层生命周期（current/memory/archive），主 agent 只做 main-orchestrator 监督、worker 必须经 sub-agent 派发的核心规则在 SKILL.md、references 和实例模板三处保持同构。
记忆生命周期设计清晰：references/memory-lifecycle.md 用表格逐文件定义了'必须同步/可以归档/禁止归档'三类边界，配套归档前后检查清单；scripts/compact_memory.py 归档后默认重建可通过严格校验的空热状态，保证实例始终处于可校验形态。
工具链全部为纯标准库 Python、带类型注解、单一职责，确定性强：init/validate/paths/render_dag/compact/safety-scan 六个脚本无第三方依赖，validate_agent_group.py --strict 能校验 tasks.csv 列形态、status/risk 枚举、depends_on 自引用与未知引用、STATE.md 与 worker 输出的 11 个标准标题。
发布安全做得超出同类技能包平均水平：scripts/check_public_safety.py 有 9 类规则（云 token、私钥/JWT、个人邮箱、凭证赋值、真实用户路径、设备标识、运行时 UUID、误粘贴提示、性能报告路径），支持 --git-history 扫描全部可达历史与提交元数据，并接入 .github/workflows/public-safety.yml 在 push/PR 强制执行。
宿主路径中立：scripts/agent_group_paths.py 用环境信号区分 Claude Code 与 Codex，并在其余宿主上默认使用 .agent_group/；已有的 .claude/agent_group 与 .codex/agent_group 实例仍可解析。安装方式是把技能目录复制到宿主 skills 路径，技能包根目录由脚本文件位置解析。
examples/ 提供两套完整实例 fixture（sample 中立回归样例 + edge-llm-research 领域样例），worker 输出、tasks.csv 的 depends_on DAG、memory 台账都填充了符合契约的内容，可同时用于回归测试和文档示范。

⚠️ 主要差距（12 项）

编排能力：失败重试与终止条件无量化契约
references/sub-agent-execution.md 的 Scheduling Rules 仅有一句'On sub-agent failure, mark the task as blocked or retry with a narrowed prompt'，没有最大重试次数、超时、退避策略、单任务/全局预算上限或全局终止条件（如最大迭代轮次、最大派发 worker 数）。current/tasks.csv 的 schema（references/memory-schema.md、assets/templates/instance/current/tasks.csv）也没有 attempt/retry_count/timeout/deadline 列，orchestrator 陷入'派发-失败-换提示重试'循环时无任何机制强制收敛。
编排能力：DAG 无环检测与就绪调度支持缺失
scripts/validate_agent_group.py 的 strict 模式只检查 depends_on 自引用和未知任务 ID（第 129-136 行），不做环检测；scripts/render_task_dag.py 也只是逐行输出 Mermaid 边，不做拓扑排序。若 tasks.csv 出现 A→B→A 互相依赖，校验通过但按'Respect dependencies before dispatching'规则执行会死锁。此外没有任何脚本能输出'当前可派发的就绪任务集合'，就绪判断完全依赖 LLM 阅读 CSV，缺少确定性工具支撑并行派发。
编排能力：并行派发只有一句 prose，无并发控制原语
references/sub-agent-execution.md 只说'Dispatch independent workers concurrently when the backend supports parallel sub-agents'，但 config.yml 模板（assets/templates/instance/config.yml）没有 max_parallel_workers 之类的并发上限配置，tasks.csv 没有锁/占用（owner claim）语义，两个并行 sub-agent 同时写 current/tasks.csv 或 current/STATE.md 时没有任何文件锁或合并规则——与 README 自述的'无并发控制'一致，但契约层连约定式规避（如仅 orchestrator 可写 tasks.csv）都未明文化。
记忆系统：长期台账无界增长，压缩只覆盖 current/
references/memory-lifecycle.md 明确 memory/TASK_LEDGER.md、PROGRESS_LEDGER.md、DECISIONS.md、RISKS.md 为追加式且'不应归档'，scripts/compact_memory.py 的 CURRENT_FILES 列表（第 11 行）只移动 current/ 下 5 个文件和 agent_outputs/。项目长期运行后台账会无限膨胀，没有任何分卷（rollover）、摘要压缩或分层索引机制，最终热路径读取（skill 要求每次 sync 前读台账）会撑爆上下文窗口。
记忆系统：无检索机制与跨项目复用能力
记忆消费方式只有'整文件阅读'：workflows/memory-sync.md 要求顺序读取 STATE.md/tasks.csv/agent_outputs，没有任何按任务 ID、关键词、时间范围检索台账条目的脚本；memory/ 完全绑定单实例路径，没有跨项目导出/导入（如把某项目的 PROJECT_FACTS/DECISIONS 提炼为可复用知识包）或全局用户级记忆层的设计。assets/templates/instance/memory/DOC_REGISTRY.yml 只是空的 documents: []，没有任何脚本或契约说明如何维护和查询它。
记忆系统：模板 frontmatter 与 references/memory-schema.md 存在 schema 漂移
assets/templates/instance/rules/*.md 和 compact_memory.py 重建的 STATE.md 都带 ag_schema: v1 的 YAML frontmatter（doc_id/authority/lifecycle/read_policy 等字段），但 references/memory-schema.md 完全没有定义 frontmatter 规范，validate_agent_group.py 也不校验它；DOC_POLICY.yml、DOC_REGISTRY.yml、tasks.meta.yml（memory-lifecycle.md 和 compact_memory.py 都引用了它）三个文件在 references/ 中均无 schema 定义，属于'模板先行、契约缺位'。
工程质量：测试覆盖仍然偏窄
tests/ 覆盖公开安全扫描，以及 agent_group_paths.py 的后端探测、三条标准路径和 init 冒烟。validate_agent_group.py 的依赖与 strict 标题校验、compact_memory.py、render_task_dag.py，以及 init→validate→compact→validate 端到端链路仍然缺少单测。
工程质量：CI 与静态检查缺失
.github/workflows/public-safety.yml 是唯一 workflow，仅跑安全扫描、unittest discover 和 examples/sample 严格校验；没有 ruff/flake8 lint、mypy 类型检查（脚本已写类型注解但从未被检查）、Python 多版本矩阵（scripts 用了 3.10+ 的 X | None 语法但未声明最低版本）。路径与 init 冒烟随 unittest 进入 CI，但没有独立的多宿主安装检查。仓库无 pyproject.toml，无法声明 requires-python。
生态与分发：版本策略与变更管理缺位
技能包通过复制目录安装，不再携带宿主 plugin manifest。仓库仍无 CHANGELOG.md、无 git tag、无版本升级/schema 迁移策略说明；ag_schema: v1 出现在模板 frontmatter 中但没有版本协商机制（validator 不识别 v1 之外的实例该如何处理）。
生态与分发：示例广度不足
examples/ 只有 sample 和 edge-llm-research 两套，且全部是 R0/R1 只读研究型流程；没有覆盖核心实现 DAG（architect → user gate → kernel-dev → runner，即 references/routing-policy.md 中的 'Core implementation' 模式）、R3/R4 门禁触发、任务 blocked/重试、双实例并存冲突、跨阶段归档后恢复等关键场景的示例，用户无法从示例学到风险门禁和失败处理的实际形态。
可观测性：无结构化执行轨迹与成本统计
唯一的执行留痕是 current/agent_outputs/*.md 里 prose 形式的 'Sub-Agent Reference' 标题（references/output-contract.md），没有结构化事件日志（派发时间、开始/结束时间戳、重试次数、token/成本、backend 会话 ID 的 JSONL 轨迹文件），与 README 自述'无遥测'一致。这导致 review workflow 要求的'验证输出确由 sub-agent 产生'实际上不可机器验证——只能相信 Markdown 里自报的引用字符串，orchestrator 违规亲自代工时无从检测。
可观测性：DAG 可视化功能过于单薄
scripts/render_task_dag.py 仅 59 行，输出裸 Mermaid flowchart 文本：无按 status 着色（done/blocked/in_progress 视觉不可区分）、无 risk 等级标注、无关键路径/就绪前沿高亮、无输出到文件或 HTML 的选项、不校验 depends_on 引用有效性（未知依赖会生成悬空节点边而不报错）、无环检测。作为唯一的可观测性工具，其信息密度不足以支撑真实监督场景。

🚨 风险清单

证据静默覆盖风险：scripts/compact_memory.py 用 shutil.move 且不检查 archive/<name>/ 是否已存在，同一 archive-name 重复执行时（POSIX 上 os.rename 语义）会静默覆盖先前归档的 STATE.md/tasks.csv 等文件，直接违反自身'归档不是删除、不得丢失证据'的核心契约（references/memory-lifecycle.md）。
契约全靠 prose 约束、无机器强制：main-orchestrator 不得代工、失败必须标记 blocked、R3/R4 必须先获门禁等关键规则都只写在 Markdown 契约里，没有 hook、轨迹校验或自动审计工具兜底；一旦宿主 LLM 未忠实执行 SKILL.md，整个监督模型失效且事后不可取证。
依赖环导致的执行死锁：validator 不检测 depends_on 环，orchestrator 按'先满足依赖再派发'执行含环的 tasks.csv 时会永久等待，且缺少全局终止条件（最大轮次/预算），无人值守场景可能无限消耗 token。
台账无界增长反噬编排质量：PROGRESS_LEDGER/TASK_LEDGER/DECISIONS 只追加不分卷，若项目跨多个 epic 长期使用，每次 memory sync 前的'读取台账'步骤会持续膨胀上下文，最终导致同步质量下降或直接超出上下文窗口——而这恰是记忆系统本要解决的问题。
多实例状态分叉：agent_group_paths.py 在 .agent_group、.claude/agent_group 和 .codex/agent_group 并存时按 backend 偏好自动选择，CLI 只打印 stderr 警告；用户在宿主间切换时，任务状态和记忆可能在多个实例中静默分叉，且没有合并或一致性检查工具。
安全扫描器误报可能侵蚀门禁公信力：personal-email 规则匹配几乎所有邮箱、personal-path 匹配所有 /home|/Users|/workspace 路径（check_public_safety.py 第 70-94 行），在真实项目文档中误报率会很高且无 allowlist/inline-suppress 机制，团队可能因噪音而绕过或关闭 CI 门禁，反而放大真实泄密风险。

方向 1：LangGraph （2 个项目 · 6 条经验）

LangGraph 多智能体编排设计调研：任务图表达、检查点/中断恢复、supervisor 与层级团队、持久化与 time-travel，及其对文件契约型轻量技能包（agent-group-orchestrator）的借鉴

LangGraph（langchain-ai/langgraph）

LangGraph 是 LangChain 生态中面向有状态、长运行智能体工作流的底层编排框架，核心抽象是 StateGraph：以共享状态（TypedDict/Pydantic schema + reducer 归并函数）为中心，节点作为计算单元、边（含条件边）作为控制流，底层采用受 Google Pregel 启发的消息传递 + super-step（超步）执行模型（事实：官方 Graph API 文档 https://docs.langchain.com/oss/python/langgraph/graph-api）。它把持久化（checkpointer 在每个超步保存 StateSnapshot）作为一等公民，在此单一基座上派生出人机协同中断（interrupt/Command）、容错恢复（durable execution）与 time-travel 调试（replay/fork）三类能力（事实：https://docs.langchain.com/oss/python/langgraph/persistence 与 https://docs.langchain.com/oss/python/langgraph/durable-execution）。多智能体方面官方定义了 network、supervisor、hierarchical teams、自定义 workflow 等架构，通过 Command(goto=..., graph=Command.PARENT) 实现节点内 handoff（事实：多智能体概念文档，https://langchain-ai.github.io/langgraph/concepts/multi_agent/）。

  • StateGraph + reducer：状态按 schema 分为若干 channel，节点只返回'增量更新'，由 reducer（如 operator.add、add_messages）决定合并语义；未指定 reducer 则覆盖写（事实，官方 Graph API 文档）
  • Pregel/BSP 超步执行：并行节点属于同一 super-step，顺序节点属于不同 super-step；每个超步结束才提交状态，形成天然的'事务边界'（事实，官方文档与 reference.langchain.com/python/langgraph/graph/state）
  • 条件边 add_conditional_edges：路由函数读取当前状态返回下一节点名，实现数据驱动分支（事实，https://reference.langchain.com/python/langgraph/graph/state/StateGraph/add_conditional_edges）
  • Send API 动态扇出（map-reduce）：条件边返回 Send 对象列表，可在运行时按数据量动态派生 N 个并行节点实例，每个实例携带独立子状态；下游普通边作为 fan-in 汇聚点，LangGraph 保证所有分支完成后才执行 reduce 节点（事实，https://reference.langchain.com/python/langgraph/types/Send）
  • Checkpointer + thread_id：每个超步持久化一份 StateSnapshot（channel 值、下一步待执行节点、config、metadata、pending tasks），thread_id 是恢复执行的主键；实现从 InMemorySaver 到 Postgres/DynamoDB 可插拔（事实，https://docs.langchain.com/oss/python/langgraph/persistence）
  • interrupt/Command 人机协同：interrupt() 在节点内暂停并落盘状态，可挂起数小时到数天，用 Command(resume=...) 携带人类输入恢复；恢复语义是'重跑该节点'而非从中断行继续，因此要求节点幂等（事实+社区实践警示，https://docs.langchain.com/oss/python/langgraph/durable-execution 与 Medium 复盘文）
  • durability 模式：提供多档持久化时机（如 sync/async/exit），在可靠性与写入开销间权衡（事实，官方 durable-execution 文档）
  • time-travel：get_state_history 遍历检查点树（类似 git commit 历史），以 checkpoint_id 重放；update_state(as_node=...) 修改历史状态后 fork 出新分支，检查点前的节点不重跑、之后的节点全部重执行（事实，https://docs.langchain.com/oss/python/langgraph/use-time-travel）
  • 多智能体 handoff：节点返回 Command 对象同时携带控制流（goto）与状态更新（update），可跨子图边界（Command.PARENT）；把'去哪'的决策放进节点而非静态边（事实，多智能体概念文档）
  • supervisor 模式：中心 supervisor 节点用 LLM 结构化输出决定下一个 worker，worker 完成后交回 supervisor 复核，不满意可退回重做形成反馈环；官方实践建议 supervisor 只保留 route/finish 能力、不挂业务工具（事实+生态经验，https://github.com/langchain-ai/langgraph-supervisor-py）
  • hierarchical teams：每个子团队有自己的 sub-supervisor 和局部状态，顶层 supervisor 只在团队粒度路由，团队内部消息历史不必上浮到全局（事实，官方教程与 langchain-opentutorial）
langgraph-supervisor-py（官方 supervisor 库）

LangGraph 官方的层级多智能体封装库：create_supervisor() 一行创建'supervisor 管 worker'的编译图，支持 supervisor 套 supervisor 组成多级团队。核心是基于工具调用（tool-calling）的 handoff 机制与可配置的消息历史管理（转发全量历史 vs 只转发最终结果）。值得注意的是（事实）：LangChain 现已建议多数场景直接用工具调用实现 supervisor 而非依赖该库，理由是直接实现对上下文工程（context engineering）控制力更强——这对'契约文档 + prompt'型插件是一个有利佐证。

  • create_supervisor([...worker...]).compile()：声明式组装 supervisor-worker 拓扑，supervisor 可嵌套形成层级（事实，README）
  • tool-based handoff：把'移交给 agent X'建模为一次工具调用，天然获得参数校验与审计记录（事实，README）
  • 消息历史裁剪策略：可选择向 supervisor 回传 worker 的完整过程消息或仅最终答复，控制上下文膨胀（事实，README）
  • 官方转向建议：推荐直接用 tool-calling 手写 supervisor 以精细控制注入 worker 的上下文（事实，reference.langchain.com/python/langgraph-supervisor 页面说明）

把'每步落盘的状态快照'升级为一等公民：为编排循环定义显式的 StateSnapshot 契约

Microsoft AutoGen (autogen-agentchat v0.4+，含 0.2 遗留 GroupChat)

微软的多智能体编程框架，核心抽象是 Team（RoundRobinGroupChat / SelectorGroupChat / Swarm 等）+ 可组合终止条件 + 可序列化团队状态。SelectorGroupChat 用一个模型充当'选主持人'，基于对话历史与各 agent 的 description 动态选择下一个发言者；0.2 时代的 GroupChat 还支持把发言者转移建模为有限状态机（FSM）图约束。事实：项目现已进入社区维护模式，微软将新项目引导到 Microsoft Agent Framework。

  • SelectorGroupChat 发言者选择（事实，来自 https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html ）：selector_prompt 模板（含 {roles}/{participants}/{history} 占位符）让模型只返回下一个角色名；candidate_func 先对候选 worker 做确定性过滤再交给模型选；selector_func 可完全绕过模型做纯规则选择（返回 None 时回退到模型）；allow_repeated_speaker 控制是否允许连续同一发言者；max_selector_attempts=3 限制模型选择重试次数。
  • 0.2 版 GroupChat 的四种 speaker_selection_method（auto/manual/random/round_robin）+ allowed_or_disallowed_speaker_transitions 图约束：把'谁能接谁的话'声明为一个有向图（FSM），LLM 只在图允许的候选集中选择；agent 的 description 字段承担'转移条件'的语义（事实，来自 https://microsoft.github.io/autogen/0.2/blog/2024/02/11/FSM-GroupChat/ ）。自定义选择函数返回 None 即终止对话。
  • 组合式终止条件（事实，来自 https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html ）：MaxMessageTermination、TextMentionTermination（可用 sources= 限定只有特定 agent 说出该词才终止）、HandoffTermination 等，可用 | 和 & 组合；条件是有状态的，触发后必须 reset 才能复用；不设终止条件则无限运行——终止是显式外置策略，不藏在 agent 内部。
  • 失败恢复与状态持久化（事实，来自 https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/state.html ）：team.save_state() 返回可 JSON 序列化的字典（含所有参与 agent 的状态），可写盘后用 load_state() 在新建的 team 上恢复并继续对话；终止条件在每次 run 后自动 reset，直接再次 run 即可'断点续跑'；运行中调用 save_state 会抛 RuntimeError（必须先停下）。
  • 评测与可观测性：agbench（仓库 python/packages/agbench，事实）是独立 CLI 评测工具，用 Docker 隔离每个任务、从干净初始状态重复运行、集中收集日志再由 metrics 脚本统计，曾用于在 GAIA/AssistantBench/WebArena 上评测 Magentic-One（ https://arxiv.org/abs/2411.04468 ）；运行时观测官方博客推荐 AgentOps 两行代码接入，监控 LLM 调用、成本、失败与多 agent 交互（ https://microsoft.github.io/autogen/0.2/blog/2024/07/25/AgentOps/ ）。
OpenAI Agents SDK (openai-agents-python，前身为实验项目 Swarm)

OpenAI 的轻量 agent 框架，抽象极少：Agent（指令+工具）、Handoff（agent 间交接）、Guardrail（输入/输出/工具三层护栏）、Session/RunState（状态）、内置 Tracing。Runner 负责跑循环：产出 final output 即停、遇 handoff 换 agent 重入循环、否则执行工具调用后继续，超过 max_turns 抛 MaxTurnsExceeded。设计哲学是'把编排循环交给 SDK，把策略写成小函数'。

  • Handoff 即工具（事实，来自 https://openai.github.io/openai-agents-python/handoffs/ ）：交接目标对 LLM 呈现为 transfer_to_<agent_name> 工具；handoff() 支持 tool_name_override、on_handoff 回调、input_type（要求交接时附带结构化参数）、input_filter（交接时裁剪/改写传给下游 agent 的历史，如内置的移除全部工具调用记录）；官方提供 RECOMMENDED_PROMPT_PREFIX 让 agent 理解交接语义。handoff 只在单次 run 内生效。
  • 三层 Guardrails 与 tripwire（事实，来自 https://openai.github.io/openai-agents-python/guardrails/ ）：input guardrail 只作用于链条第一个 agent，tripwire 触发则 agent 根本不执行（省 token、避免工具副作用）；output guardrail 只作用于产出最终输出的 agent，触发则抛 OutputGuardrailTripwireTriggered 异常；tool guardrail 在每次 function tool 调用前后执行。护栏与 agent 就近绑定（colocate）以提高可读性。
  • 终止与失败恢复（事实，来自 https://openai.github.io/openai-agents-python/running_agents/ 与 /human_in_the_loop/ ）：终止条件 = '产生了 output_type 类型的 final output' 或 max_turns 上限（超限抛 MaxTurnsExceeded 防死循环）；异常体系区分 GuardrailTripwireTriggered / ModelBehaviorError 等便于 try/except 分类处置；RunState 是可序列化快照（to_string/from_string 存 JSON），需要人工审批的工具调用会记录为 interruption 而非直接执行，应用 approve/reject 后用同一 state 恢复运行——审批可以跨进程、跨时间。
  • 多轮状态续接的四种方式（事实，来自 https://openai.github.io/openai-agents-python/results/ ）：result.to_input_list()（客户端自管全量历史）、session（SDK 持久化历史）、conversation_id / previous_response_id（服务端托管），按'谁拥有历史'选择。
  • Tracing 默认开启（事实，来自 https://github.com/openai/openai-agents-python/blob/main/docs/tracing.md ）：每次 run 自动生成 trace 及 span，覆盖 LLM 生成、工具调用、handoff、guardrail 检查与自定义事件；TracingProcessor 插件接口可导出到 OpenAI Traces 仪表盘或 Langfuse/W&B 等第三方后端；可用环境变量 OPENAI_AGENTS_DISABLE_TRACING=1 关闭，文档强调对敏感数据要禁用内容采集。评测侧主要依托 Traces 仪表盘做调试与回放，未内置类似 agbench 的基准工具（推测：因其定位是轻量 SDK，评测交给平台侧）。

CrewAI 与 MetaGPT 多智能体编排机制调研——对 agent-group-orchestrator 在 worker registry、路由策略、输出契约上的借鉴

CrewAI

CrewAI 是一个角色扮演式多智能体编排框架（Python），核心抽象是 Agent（角色）、Task（任务）、Crew（团队）与 Process（流程），并在其上叠加事件驱动的 Flows 编排层。它的定位是"Crew 负责协作、Flow 负责流程控制"：Crew 内部由 LLM 自主协作与委派，Flow 则用装饰器把 Crew/LLM 调用编织进确定性的、可持久化的状态机。配置推荐使用 agents.yaml / tasks.yaml 的声明式方式，任务输出可通过 Pydantic 模型与 guardrail 做机器校验。

  • 角色定义三元组（事实，来自官方文档 https://docs.crewai.com/en/concepts/agents）：role（职位）、goal（目标）、backstory（背景/专长），外加 tools、llm、max_iter、max_rpm、memory、cache、verbose 等属性；社区最佳实践强调"专才优于通才"，且约 80% 精力应放在任务设计而非角色设计上。
  • 显式委派开关（事实，https://docs.crewai.com/en/concepts/collaboration）：allow_delegation=True 时 agent 自动获得 "Delegate work to coworker" 与"向同事提问"两个协作工具；防止委派失控的做法是：在 backstory 中写清职责边界、限制 max_iter、对底层执行者关闭 allow_delegation。
  • Process.sequential 与 Process.hierarchical（事实，https://docs.crewai.com/en/learn/hierarchical-process）：默认 sequential 按任务列表顺序执行；hierarchical 必须配置 manager_llm（自动生成带协调提示词的 manager agent）或自定义 manager_agent，manager 必须不在 agents（worker）列表内；hierarchical 下任务可不指定 agent，由 manager 依据各 agent 的 role/goal 动态指派，并在推进前验证结果、必要时重新委派。已知代价与坑（事实，来自文档与 issue #4783、#2606）：每次 manager 决策都是一次 LLM 调用，弱 manager 会产生循环或不完整的委派，且委派工具的参数 schema 曾出现类型错误。
  • Task 输出契约（事实，https://docs.crewai.com/en/concepts/tasks）：每个 Task 必须写 expected_output（对结果形态的自然语言描述，属软约束）；output_json / output_pydantic 用 Pydantic 模型做硬校验（校验失败会自动让 LLM 重试修复）；context=[上游任务] 显式声明数据依赖，把上游结构化输出注入下游提示词，避免下游因信息缺失而幻觉。
  • Task Guardrail 质量门禁（事实，https://docs.crewai.com/en/concepts/tasks）：函数式 guardrail 接收 TaskOutput 返回 (bool, Any)，失败时把原因反馈给 agent 重做；字符串式 guardrail 自动生成 LLMGuardrail 用 LLM 按描述评审输出；可叠加多层，并需谨慎设置重试上限（重试少=流程更严格，重试多=更有创造空间）。
  • Flows 事件驱动编排（事实，https://docs.crewai.com/en/guides/flows/first-flow）：@start 定义入口，@listen 监听上游步骤完成，@router 检查状态后返回字符串路由到匹配的下游分支，配合 or_/and_ 组合条件；状态支持 dict（非结构化）或 Pydantic（结构化+校验），每次执行自动分配 UUID，支持 @persist 持久化与断点恢复，还能把流程渲染成 HTML 可视化图。
  • 声明式配置（事实，https://docs.crewai.com/en/concepts/tasks 与 DeepWiki）：agents.yaml/tasks.yaml 存放 role/goal/backstory 与 description/expected_output/agent/context，支持 {topic} 变量插值；Python 侧用 @CrewBase 装饰器把 YAML 中的名字解析到 agent/task/tool/输出模型实例。
MetaGPT

MetaGPT（ICLR 2024 论文，arXiv:2308.00352）是把人类软件公司的标准作业程序（SOP）编码进多智能体协作的元编程框架，口号是 "Code = SOP(Team)"：输入一行需求，产出 PRD、竞品分析、系统设计、任务清单直至代码仓库。其最鲜明的设计是：agent 之间不靠自由对话通信，而是以结构化文档（PRD/设计文档/任务表/代码）作为通信介质，通过全局消息池 + 发布-订阅机制流转，从机制上抑制对话式幻觉与信息过载。

  • SOP 化装配线（事实，论文 https://arxiv.org/abs/2308.00352）：ProductManager 产出含 User Stories 与 Requirement Pool 的 PRD → Architect 产出系统模块设计与交互时序（含接口定义、UML）→ ProjectManager 拆解为任务清单 → Engineer 实现 → QA Engineer 写并跑测试；SOP 为每个角色规定职责、中间产物的确切格式与质量标准，形成清晰的交接协议。
  • 文档即接口（事实，论文对比 ChatDev 一节）：agent 间通过文档与图表而非对话沟通，文档必须包含下游所需的全部信息，"防止无关内容与信息缺失"；每类 Action（如 WriteDesign）自带输出 schema、校验与重试逻辑，是可复用可替换的模块。
  • 全局消息池 + 发布-订阅（事实，论文与官方教程 https://docs.deepwisdom.ai/main/en/guide/tutorials/multi_agent_101.html）：所有 agent 把标准化输出 publish 到共享消息池，各角色按 _watch([上游Action]) 订阅相关消息（如 Architect 订阅 WritePRD、QA 订阅 Engineer 的代码），过滤无关上下文以避免信息过载与上下文窗口爆炸；后续版本把 subscription 演化为 tags。
  • Role 运行循环（事实，官方教程）：_observe 从环境取被 watch 的消息 → _think 选定待执行 Action → _act 执行并把结果封装为 Message 发布回环境；每步都与角色 Memory 交互。组队方式：Team().hire([各角色]) + invest(预算) + run_project(idea) + run(n_round)。
  • 可执行反馈质量门禁（事实，论文）：Engineer 在运行时执行并调试自己生成的代码，迭代修正；消融实验显示该机制在 HumanEval 上带来 4.2%、MBPP 上 5.4% 的 Pass@1 绝对提升（整体 85.9%/87.7%）；另支持 use_code_review 开启代码评审、--run-tests 触发 QA 动作，甚至可用 is_human=True 把人类接入为评审者。
  • 增量开发模式（事实，https://docs.deepwisdom.ai/v0.5/en/guide/in_depth_guides/incremental_development.html）：--inc 配合 --project-path 基于既有仓库迭代，新需求累积进现有 PRD，再基于当前 PRD 重跑流水线；--max-auto-summarize-code 限制自动代码总结轮数。
  • 已知局限（事实+社区评论）：线性 SOP 流水线偏脆——PRD 发布后缺少 Engineer 反向质疑需求并触发精化循环的内建机制；成本方面论文报告单示例分析+设计约 $0.2、完整项目约 $2.0（GPT-4 时期数据）。

方向 5：记忆系统 （6 个项目 · 6 条经验）

开源智能体记忆系统调研：分层记忆、抽取更新流水线、记忆生命周期与 Markdown/向量/图记忆实践，及其对 agent-group-orchestrator 三层 Markdown+CSV 记忆的改进启示

Letta / MemGPT

源自 UC Berkeley 的 MemGPT 论文（2023），把 LLM 看作运行在受限上下文上的操作系统进程，提出'虚拟上下文管理'。现已发展为以持久化状态为默认的通用 agent 平台。其记忆架构与本仓库的 current/memory/archive 三层最为同构：core≈current/STATE.md，recall≈ledger，archival≈archive/。

  • 三层记忆层级（事实）：Core Memory 常驻上下文窗口（类比 RAM），是有标签、有容量预算的 memory block（如 persona/human/自定义任务块）；Recall Memory 是可搜索的完整对话历史（类比磁盘缓存）；Archival Memory 是经处理索引后的长期知识库，实现上用 PostgreSQL + pgvector 向量检索。
  • 自编辑记忆（事实）：agent 在推理循环中通过工具调用（core_memory_append / core_memory_replace、archival 插入与搜索）自主决定记什么、改什么；代价是记忆质量完全依赖模型判断，且每次记忆操作消耗推理 token。
  • Sleep-time compute（事实，Letta 2025-04 白皮书）：把记忆整理从对话热路径剥离，由共享 memory block 的后台 sleep-time agent 在空闲期异步重组记忆，把'原始上下文'加工成'已学习上下文'；主 agent 每走 N 步触发一次，频率可配。
  • 取舍（来自第三方对比，事实性引用）：自编辑方式自适应但不可预测——模型没存的东西就丢了；这正是'契约化 SOP + 校验器'这类确定性方案的对立面。
Mem0

定位为可插拔的生产级长期记忆层（论文 arXiv:2504.19413）。核心是'抽取 + 更新'两阶段流水线：先用 LLM 从新消息对中抽取候选事实，再检索 top-k 相似旧记忆，由 LLM 通过工具调用裁决每条候选事实的去留，是目前最清晰的记忆冲突消解操作语义。

  • 四操作裁决（事实，来自论文）：ADD（全新信息新建）、UPDATE（补充/修正/刷新已有记忆）、DELETE（新信息与旧记忆矛盾时删除）、NOOP（重复或无关则不动）；论文配置为参考最近 10 条消息 + 10 条相似记忆。
  • 图变体 Mem0g（事实）：抽取实体与关系三元组，配 Conflict Detector 标记重叠/矛盾的节点与边，Update Resolver 决定合并、失效或跳过；支持把关系标记为 obsolete 而非物理删除，以保留时间线。
  • 成本教训（事实性分析）：每次写记忆需要 2 次 LLM 调用 + 1 次向量检索，100 轮对话仅记忆管理就要 200+ 次调用——说明'每步都做智能消解'在编排场景不划算，应放在阶段边界批量做。
  • 工程告警（事实，GitHub issue #4896）：v2.0.0 曾退化为 ADD-only + MD5 精确去重，与文档宣称的冲突消解不符，矛盾事实被并存写入——'文档承诺的消解语义'必须有测试/校验兜底，否则会静默失效。
LangMem (LangChain)

LangChain 团队的长期记忆 SDK，按认知科学把 agent 记忆分为语义（事实）、情景（经历）、程序性（行为规则）三类，并提供'热路径工具调用'与'后台异步整理'两种集成模式。存储后端无关（KV/Postgres/向量库均可），靠命名空间做多租户隔离。

  • 三类记忆（事实）：semantic=事实与用户画像（支持无界 collection 与单文档 profile 两种形态）；episodic=过去交互的情节摘要，可作 few-shot 范例；procedural=agent 自我更新提示词规则，实现行为层自我改进。
  • 后台整合（事实）：BackgroundMemoryManager 在会话外异步运行，对比新内容与既有记忆后并行发出 create/update/delete 工具调用；抽取提示词可配置，用于在'覆盖面'与'去重合并'之间调平衡。
  • 整合防膨胀（事实）：通过合并相关记忆、消解矛盾避免'记忆囤积'（memory hoarding）导致的无界增长。
  • 运维教训（事实性引用）：有评测指出其检索 p50 延迟高达 ~18s，不适合同步热路径——再次印证记忆整理应离线/异步化。
Zep / Graphiti（时间知识图谱记忆）

Graphiti 是开源时间知识图谱引擎（论文 arXiv:2501.13956），Zep 是其上的记忆服务。核心贡献是双时间轴模型与'边失效'：新事实到来时不删除旧事实，而是给旧边打上失效时间戳，查询时取指定时点的有效切片，实现无损的矛盾消解与时间推理。

  • 双时间轴（事实）：同时记录事件时间 T（事实何时发生）与摄入时间 T'（系统何时观察到），每条边带四个时间戳：t_created/t_expired（系统内创建/失效）与 t_valid/t_invalid（事实真实有效区间）。
  • 边失效代替删除（事实）：新边可使旧边失效（invalidate not delete），被取代的事实保留可溯源；这与本仓库 DECISIONS.md 的 supersedes、RISKS.md 的状态机（active/mitigated/closed/accepted）是同一思想的图谱化版本。
  • 非损失设计（事实）：情节边把 episode（原始证据）与抽取出的实体/事实双向关联，语义结论可回溯到原始来源做引用——对应 ledger 摘要必须引用 agent_outputs/ 原始证据的契约。
  • 实时增量摄入（事实）：区别于 GraphRAG 的静态文档摘要，支持流式更新与混合检索（向量+BM25+图遍历）。
MemoryBank（Ebbinghaus 遗忘曲线记忆衰减）

较早提出用艾宾浩斯遗忘曲线做 LLM 记忆衰减的工作：记忆强度 R=e^(−t/S)，被召回的记忆强度增强，久未访问的记忆衰减淘汰；存储上按'日事件摘要 + 全局画像'分层，FAISS 稠密检索。后续工作（FadeMem、H-MEM 等）扩展了多维强度模型。

  • 指数衰减 + 召回强化（事实）：R=e^(−t/S)，访问即重置/增强强度，实现'用进废退'。
  • 分层摘要存储（事实）：对话日志 → 每日事件摘要 → 全局 portrait，逐级压缩。
  • 重要告警（事实，来自 A-MEM 实验与综述）：基于遗忘曲线的管理能控制记忆规模、降低检索时间，但会造成任务性能显著下降；规则式衰减只是'有用性'的间接代理，可能丢弃语义重要但低频的信息——因此工程上更稳妥的是'标记 stale 而非删除'。
  • FadeMem 改进（事实）：按语义相关性、访问频率、时间模式做差异化衰减速率，配 LLM 引导的冲突消解与记忆融合，宣称减少 45% 存储。
Markdown-first 记忆实践（memweave / Manus / Claude Code CLAUDE.md 与 auto memory）

业界近期的实践收敛：Manus、Claude Code 等高营收 agent 产品均以纯 Markdown 文件为主记忆而非托管向量库，理由是可审查、可 diff、git 原生、无供应商锁定。核心架构原则是'存储与检索索引分离'：Markdown 是唯一事实源，任何索引（向量/BM25/SQLite）都是可随时删除重建的派生物（memweave 项目即此实现，见 https://towardsdatascience.com/memweave-zero-infra-ai-agent-memory-with-markdown-and-sqlite-no-vector-database-required/）。

  • 存储/检索分离（事实性共识）：Markdown+YAML frontmatter 为 canonical 存储，索引是 disposable artifact，可零损失重建——这为纯标准库仓库提供了'不引入向量库也能升级检索'的路径。
  • 先解决策展再解决检索（事实性观点，多智能体团队实践）：早期 agent 的瓶颈是'不知道什么值得记、查询模式是什么'，先建向量层是'快速做错事'；Markdown-first 让你先观察访问模式再优化。
  • CLAUDE.md 实践（事实）：CLAUDE.md 建议 <200 行、命令优先、用 @docs/xxx.md 引用而非粘贴（上下文填满会导致模型指令遵循度下降，即 context rot）；Claude Code 的 auto memory 存于 ~/.claude/projects/<project>/memory/，MEMORY.md 仅前 200 行随启动加载——'热记忆有硬预算'是普遍做法。
  • 适用边界（事实性观点）：Markdown 适合上下文有限、结构化的项目本地 agent；企业级大规模多租户记忆才需要数据库方案。

OpenHands (原 OpenDevin)

MIT 协议的开源软件工程代理平台（ICLR 2025 论文），核心是事件流架构：Agent 产出 Action，Runtime 在隔离沙箱中执行并返回 Observation，所有交互作为类型化事件流经中央 pub/sub 枢纽。V1 重构为模块化 Agent SDK，全部 action/observation 记录为不可变事件的 append-only EventLog，官方明确以此支撑确定性回放、暂停/恢复与调试。事实来源：GitHub 仓库、ICLR 2025 论文（https://proceedings.iclr.cc/paper_files/paper/2025/file/a4b6ad6b48850c0c331d1259fc66a69c-Paper-Conference.pdf）与 SDK 论文（https://arxiv.org/html/2511.03690v1）。

  • 评测解耦（事实）：run-batch 只产轨迹与 preds.json，评测由 SWE-bench harness 单独执行；另有 quick-stats/compare-runs/merge-preds 等运行间对比命令
Aider

结对编程 CLI 工具，是'benchmark 驱动开发'的代表：自建代码编辑基准（早期 133 题 Exercism Python，后升级为 225 题六语言 polyglot 基准），凡改 prompt、编辑格式或模型配置必跑基准，用量化分数决定是否合入。repo map 用 tree-sitter 提取符号并在 token 预算内选取最重要部分，帮助 LLM 理解大仓库。

  • polyglot 基准（事实）：225 道 Exercism 练习覆盖 C++/Go/Java/JS/Python/Rust，两次尝试制（第一次失败则展示单测结果再试），主指标 pass_rate_2（https://aider.chat/docs/leaderboards/）
  • 过程合规指标（事实）：'well-formed edits / percent using correct edit format' 度量模型是否遵守编辑格式契约——不仅测结果对不对，还测是否守规矩；违规时给反馈并要求重发修正版
  • 编辑格式即契约（事实）：whole/diff 等格式按模型基准表现在 aider/resources/model-settings.yml 固化为默认；architect/editor 角色拆分（推理与编辑分离）也由基准验证出 SOTA（85%）后才采纳（https://aider.chat/2024/09/26/architect.html）
  • 可复现性（事实）：基准输出 YAML 记录全部生效配置 + 仓库 git hash（有未提交改动标 dirty），model+edit_format+commit_hash 即可复现任一次运行（https://github.com/Aider-AI/aider/blob/main/benchmark/README.md）
  • 回归门禁文化（事实）：release notes 中直接写'Benchmarked at 63.9%, no regression'，prompt 级改动也过基准验证
  • repo map（事实）：tree-sitter 提取类/函数签名，按重要性排序装入 --map-tokens 预算（默认 1k），替代早期 ctags 方案（https://aider.chat/docs/repomap.html）
  • 评测安全（事实）：基准在 Docker 容器内跑，因为 harness 会无人工审查地执行 LLM 生成的代码
SWE-bench（评测基准生态，作为三者共同的回归评测底座）

以真实 GitHub issue + 金标测试补丁为核心的软件工程代理基准，是 OpenHands 与 SWE-agent 的共同回归评测底座。评测与推理分离：代理只产 preds.json（补丁预测），由独立 harness 在实例级 Docker 镜像中跑测试判定 resolve；衍生出 Verified/Live/Multimodal/SWT-Bench 等变体覆盖不同能力面。

  • 推理/评测分离（事实）：代理产出预测文件，评测由独立 harness 执行，避免评测逻辑污染代理核心
  • 实例级环境固化（事实，OpenHands benchmarks 文档）：每个实例按仓库+issue 预构建专用 Docker 镜像并推送公共 registry，特殊依赖（如 sphinx-doc 需 docutils<0.21）用 allowlist 加层，保证环境可复现
  • 隔离并行（事实）：评测实例在隔离容器中运行，支持 32+ worker 大规模并行
  • 多维变体（事实）：SWE-bench Verified（人工核验）、SWE-bench-Live（防污染的新题）、SWT-Bench（测试生成能力）等，说明单一指标不足以覆盖代理能力面

对本仓库的可落地经验

教训一：把'编排轨迹'升级为一等公民——append-only 结构化事件日志，而非仅靠 Markdown 报告
OpenHands 的核心可靠性机制是所有 Action/Observation 记录为不可变事件的 append-only EventLog（事实），SWE-agent 则把每次运行的 .traj 与 config 同目录留存（事实）。两者共同点：轨迹是机器可读、可回放、可与评测结果关联的结构化数据，而不是给人看的散文。目标仓库当前的留痕是 current/agent_outputs/<task_id>_<worker>.md 加 output-contract 中'记录 backend 与 sub-agent reference'的软性要求，人可读但机器不可校验、不可回放（推测：一旦 worker 数量或轮次增多，仅靠 Markdown 将无法做自动化质量分析）。
在 references/output-contract.md 中新增机器可读附件要求：每次编排在 current/agent_outputs/ 旁产出 events.jsonl（每行一条事件：ts、task_id、worker、backend、sub_agent_ref、event_type=dispatch/output/gate/retry/block、artifact 路径），由 workflows/orchestrate.md 第 8/10 步强制写入；scripts/render_task_dag.py 顺势扩展为可叠加 events.jsonl 的执行状态着色（dispatched/done/blocked），使 tasks.csv 的静态 DAG 与实际执行轨迹可对照。compact_memory.py 归档时将 events.jsonl 一并落入 archive/，形成可追溯台账。
教训二：借鉴 SWE-agent 的 traj-to-demo / run-replay，建立'金标编排轨迹'作为回归 fixture
SWE-agent 的闭环是：录制轨迹 → traj-to-demo 转成可手工编辑的 YAML → run-replay 在环境中重放并验证（事实）。这让'一次好的运行'固化为可重复执行的测试资产。目标仓库的编排本质是确定性决策（读 goal + registry + routing-policy → 产出 worker 选择与 tasks.csv DAG），比代码代理更容易做无 LLM 的回放校验（推测：worker 选择与 DAG 结构的正确性可以离线判定，无需真实派发 sub-agent）。
以 examples/sample/ 与 examples/edge-llm-research/ 为种子建立 evaluation/fixtures/：每个 fixture 含输入（goal 描述 + config.yml + agents/ 注册表）与金标输出（期望的 tasks.csv DAG、期望选中/跳过的 worker 及理由、期望风险等级）。新增 scripts/replay_orchestration_check.py（纯标准库，延续现有 scripts/ 风格），比对实际产出的 tasks.csv/events.jsonl 与金标：DAG 边集合匹配率、worker 选择准确率、跳过理由是否记录。tests/ 目前只有 test_check_public_safety.py，把该回放校验接入 tests/ 即得到第一层编排回归测试。
教训三：Aider 式 benchmark 驱动开发——每次修改 SKILL/契约文档必须跑固定评测集，并记录 commit hash 保证可复现
Aider 的做法（事实）：凡 prompt、编辑格式、模型配置变更必跑基准，release note 直接写'no regression'；输出 YAML 记录全部配置 + git hash，三元组即可复现任一次运行。对这个技能包而言，SKILL.md 与 references/*.md 就是它的'prompt'——目前修改这些文档没有任何量化验证手段（事实：仓库 0.1.0 无 CI、无评测），改坏了路由策略只能靠人工发现（推测）。
建立 evaluation/orchestration-bench/：10-20 个标准 goal（覆盖 routing-policy.md 中四类 DAG 模式：只读分析/文档/核心实现/远程验证，以及 R0-R4 各风险档），用真实后端（Claude Code 或 Codex）跑 agent-group-orchestrate，评分维度：(a) DAG 与参考模式匹配度；(b) 越权率——main-orchestrator 是否违反 sub-agent-execution.md 亲自执行 worker 任务（可从 events.jsonl 判定无 dispatch 事件却有 worker 结论）；(c) output-contract 字段合规率（Aider 的 well-formed edits 思路——过程合规是独立指标）；(d) R3/R4 门禁触发正确率（对照 risk-policy.md）。每次运行输出 YAML 记录插件 git hash + 后端 + 模型，写入 evaluation/results/。规则：凡改 SKILL.md、workflows/*.md 或 references/routing-policy.md、risk-policy.md，PR 必须附本基准分数对比。
教训四：SWE-agent ACI 的'lint-before-apply'守护栏——把 validate_agent_group.py 扩展为派发前后的 DAG/契约 linter
SWE-agent 证明（事实，消融 +10.7pp）：在动作生效前用 linter 拦截坏编辑、并给出简洁具体的反馈，比事后补救有效得多；SWE-Bench-CL 等后继工作也复制了'编辑前 flake8'模式。对这个技能包，等价物是：在 orchestrator 派发前对 tasks.csv 做结构校验，在 worker 产出后对 output 做契约校验——错误在进入下一环节前被拦截并以明确信息反馈给 orchestrator（推测：这是提升执行可靠性成本最低的一步，因为全部可用纯标准库离线实现）。
扩展 scripts/validate_agent_group.py，新增两类检查：(1) tasks.csv DAG lint——depends_on 引用的 task id 必须存在、无环（拓扑排序检测）、id 符合 AUTO-<yyyymmdd>-<nn>（routing-policy.md 规定的格式）、status 转移合法（如 done 的任务不得依赖 pending 任务）、owner 必须在 agents/ 注册表中且非 main-orchestrator 独占实现类任务；(2) agent_outputs 契约 lint——文件名匹配 <task_id>_<worker>.md、必含 output-contract.md 列出的 task id/backend/sub-agent reference/conclusion 等段落。workflows/orchestrate.md 第 5 步（建 DAG 后）与第 8 步（写输出后）显式要求运行该校验，失败即阻断并回报，对应 SWE-agent'每回合具体简洁反馈'原则。
教训五：OpenHands microagents 的触发式知识加载——为 references/ 引入按需加载的 frontmatter 触发约定
OpenHands 的 microagents/skills（事实）：无 frontmatter 的文件常驻上下文，带 triggers 的仅在关键词命中时加载，V1 还支持按文件 glob 的 path-triggered 注入；PR #8114 进一步简化为'只有 triggers 重要'。目标仓库的 SKILL.md 已有手写的 Reference Loading 段（'需要 worker 选择时读 routing-policy.md'），本质是人肉触发规则，但格式不统一、不可被工具校验（事实：当前 references/*.md 无 frontmatter）。
为 references/ 下 9 个契约文档统一加 YAML frontmatter（triggers: [worker selection, DAG]、load: always|on-demand），workflows/*.md 的 Reference Loading 段改为引用 frontmatter 约定而非逐条硬编码；scripts/validate_agent_group.py 增加一致性检查：SKILL.md 引用的 reference 必须存在、always 级文档（如 sub-agent-execution.md 的核心禁令）必须出现在 orchestrate 工作流的第 2-3 步。收益（推测）：降低每轮编排的上下文开销，且触发规则本身成为可回归测试的数据而非散文。
教训六：评测分层与隔离——无 LLM 的确定性测试进 CI，LLM 评测独立目录/独立触发，避免 OpenHands V0 的耦合教训
OpenHands 明确的架构教训（事实，SDK 论文）：V0 单体仓库中 agent 核心吸收了 benchmark 依赖与环境 hack 导致脆弱，V1 将评测拆到独立 benchmarks 仓库；其 QA 分四层——单元测试、LLM 集成测试、示例全量运行、基准评测，且 CI 中集成测试与重型评测分开触发（issue #5076）。Aider 则把会执行 LLM 生成代码的基准放进 Docker（事实）。目标仓库当前只有 1 个单测且无 CI（事实）。
分三层落地：第一层（每次 push 的 GitHub Actions，纯标准库、秒级）——现有 tests/test_check_public_safety.py，加上 init_agent_group.py 初始化后目录结构断言（对照 directory-contract.md）、validate_agent_group.py 对 examples/sample 与 edge-llm-research 的通过性、render_task_dag.py 对样例 tasks.csv 的 Mermaid golden 输出比对、compact_memory.py 归档幂等性（对照 memory-lifecycle.md 的 current/memory/archive 三态）；第二层（PR 手动触发）——教训二的金标轨迹回放校验；第三层（发版前）——教训三的 LLM 编排基准，放独立 evaluation/ 目录并声明独立依赖，不让插件核心（scripts/ 纯标准库承诺）沾染评测依赖。

四、差异化定位与设计原则

定位：agent-group-orchestrator 应定位为“介于官方原生 subagents 与重型编排框架之间的可审计文件契约编排层”：不做运行时、不做数据库、不做神经路由（claude-flow 的反面教训），而是把 LangGraph/AutoGen 等框架中已被验证的编排语义（检查点、终止条件、guardrail、reducer、转移图）翻译成纯 Markdown+CSV 的机器可校验契约，让任何后端（Claude Code / Codex / 未来的 agent teams）的主 agent 都能以 git-diff 可审查、CI 可回归、崩溃可恢复的方式监督多 worker 协作。差异化壁垒是“每条契约都有校验器兜底 + golden fixture 回归”——这正是 66k star 的 claude-flow 缺失、8k star 的 claude-squad 用克制赢得口碑的那条护城河。

五条设计原则

  1. Markdown/CSV 是唯一事实源：任何索引、DAG 渲染、轨迹统计都是可随时删除重建的派生物，绝不引入必需的数据库或服务端组件（memweave/Manus 的存储与检索分离原则）
  2. 契约必须机检：凡写进 references/ 的规则，必须在 validate_agent_group.py 或 CI 中有对应校验，拒绝只存在于 prose 的承诺（Mem0 issue #4896 静默退化与 SuperClaude 文档漂移的教训）
  3. 归档不是删除：冲突用失效标记（superseded/stale）消解，归档做快照式落盘保证任意一轮可精确回放，证据链永不折断（Zep 边失效 + LangGraph time-travel）
  4. 预算与终止显式化：重试次数、编排轮次、门禁等待、热记忆行数都有硬上限并由校验器强制，不依赖模型自觉收敛（AutoGen 组合终止条件 + OpenAI Agents max_turns）
  5. 功能面克制：worker 角色保持个位数、skills 保持 4 个，新机制必须先在 examples/ 以 fixture 形式验证并挂上回归测试后才进 references/（claude-squad 窄范围成功 vs SuperClaude persona 膨胀的对照）
